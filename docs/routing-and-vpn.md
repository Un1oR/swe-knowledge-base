# Как пакет проходит через VPN: маршрутизация, туннели, NAT и маскировка трафика

Сетевые технологии легче изучать не как перечень протоколов, а через один сквозной вопрос:

> Что происходит с данными от вызова `send()` в приложении до удалённого сервера и обратно — напрямую, через VPN, при разделении трафика, трансляции адресов, потере пакетов и анализе трафика?

Ответ связывает почти все темы этой статьи. Приложение пишет данные в сокет; транспортный протокол превращает их в сегменты или датаграммы; IP добавляет адреса; таблица маршрутизации выбирает путь; физический либо виртуальный интерфейс принимает пакет. VPN добавляет ещё один маршрут, ещё один набор заголовков и границу шифрования. NAT меняет адрес на выходе с VPN-сервера, DNS может выбрать совсем иной путь, а DPI видит внешнюю форму зашифрованного обмена.

Цель статьи — построить эту картину от базовых понятий до практической диагностики. Детали отдельных протоколов важны, но они должны цепляться за путь пакета, а не висеть в памяти независимо друг от друга.

## Пакет внутри пакета

Допустим, приложение хочет отправить данные серверу `142.250.74.110`. Оно создаёт сокет и вызывает `send()`. Для TCP ядро сначала устанавливает соединение, а затем формирует TCP-сегменты. Для UDP один успешный `send()` передаёт одну UDP-датаграмму; ниже по стеку IP может фрагментировать её для доставки. В обоих случаях транспортные данные оказываются внутри IP-пакета с адресом назначения.

Дальше ядро принимает **решение о маршруте**: сопоставляет адрес назначения с правилами и таблицами маршрутизации. Результатом решения становится, среди прочего, выходной интерфейс и, если нужен, следующий маршрутизатор. Приложение обычно не решает само, отправлять пакет через `wlan0` или `tun0`; оно лишь задаёт адрес назначения и иногда дополнительные атрибуты сокета. Политика операционной системы делает выбор ниже по стеку.

```{mermaid}
flowchart TD
    App[Приложение] --> Socket[Сокет: send]
    Socket --> Transport[TCP-сегмент или UDP-датаграмма]
    Transport --> Inner[IP-пакет<br/>dst = 142.250.74.110]
    Inner --> Route{Маршрут для адреса<br/>назначения}

    Route -->|напрямую| Physical[Физический интерфейс<br/>wlan0 или eth0]
    Physical --> Gateway[Домашний роутер / сеть провайдера]
    Gateway --> Internet[Интернет]
    Internet --> Destination[Удалённый сервер]

    Route -->|через VPN| Tun[TUN-интерфейс]
    Tun --> VPNClient[VPN-клиент читает<br/>внутренний IP-пакет]
    VPNClient --> Encrypt[Шифрование и инкапсуляция]
    Encrypt --> OuterSocket[Сокет VPN-клиента]
    OuterSocket --> Outer[Внешний UDP- или TCP-пакет<br/>dst = VPN_SERVER_IP]
    Outer --> OuterRoute{Маршрут до<br/>VPN-сервера}
    OuterRoute --> Physical

    Internet --> VPNServer[VPN-сервер]
    VPNServer --> Decrypt[Расшифрование и декапсуляция]
    Decrypt --> Forward[Маршрутизация, firewall и NAT]
    Forward --> Destination
```

На схеме показаны два разных IP-пакета.

- **Внутренний пакет** адресован настоящему получателю, например `142.250.74.110`. Именно его приложение хотело отправить через VPN.
- **Внешний пакет** адресован VPN-серверу. Его создаёт VPN-клиент, зашифровав внутренний пакет и поместив результат в полезную нагрузку своего транспортного протокола.

На клиенте поэтому происходят два решения о маршруте. Первое направляет внутренний пакет в виртуальный интерфейс. Второе отправляет внешний пакет к VPN-серверу через реальный интерфейс. Если второе решение снова выберет туннель, получится цикл: чтобы построить туннель, потребуется уже работающий туннель.

Разделение на внутренний и внешний пакеты объясняет сразу несколько свойств VPN:

- до адреса VPN-сервера нужен маршрут в обход самого туннеля;
- заголовки туннеля уменьшают доступный MTU для внутреннего пакета;
- после расшифрования сервер должен переслать внутренний пакет дальше и обычно подменить его исходный адрес;
- провайдер видит внешний обмен с VPN-сервером, но не адрес назначения во внутреннем IP-заголовке;
- split tunneling управляет тем, какие пакеты попадут в виртуальный интерфейс;
- KillSwitch запрещает обход туннеля, сохраняя только необходимые исключения.

### Почему TCP можно передавать внутри UDP

UDP не обязан обеспечивать надёжность внешнему туннелю, чтобы внутренний TCP продолжал работать. Если внешняя UDP-датаграмма с TCP-сегментом потерялась, получатель внутреннего TCP увидит пропуск в последовательности байтов и не подтвердит потерянный диапазон. Внутренний TCP отправителя повторно передаст сегмент. VPN-клиент зашифрует новый экземпляр внутреннего пакета и отправит его в новой UDP-датаграмме.

Иными словами, потерю исправляет тот слой, которому нужна надёжность. Для TCP-трафика это внутренний TCP; для внутреннего UDP-приложения потеря останется видна приложению, если оно само или протокол VPN не добавляет надёжность. Внешний UDP сохраняет границы пакетов и не создаёт второй независимый механизм упорядочивания — поэтому он хорошо подходит для переноса произвольных IP-пакетов.

## IPv4-адреса, маски и CIDR

IPv4-адрес состоит из 32 бит. Запись `192.168.1.37` просто группирует их в четыре октета по восемь бит. Суффикс `/24` говорит, сколько старших бит относятся к **сетевому префиксу**:

```text
192.168.1.37/24
адрес:  11000000.10101000.00000001.00100101
маска:  11111111.11111111.11111111.00000000
        <------ сеть ------><-- узел -->
```

Единицы маски фиксируют сетевую часть, нули оставляют место для адресов узлов. `/24` эквивалентен маске `255.255.255.0`: первые 24 бита одинаковы у всей подсети, последние 8 меняются.

**CIDR** (Classless Inter-Domain Routing) — способ описывать сети префиксом произвольной длины вместо старых фиксированных классов адресов. Запись состоит из базового адреса сети и длины префикса: `192.168.1.0/24`.

Термины удобно развести явно:

- **подсеть** (subnet) — множество адресов с общим сетевым префиксом;
- **маска сети** (netmask) — 32 бита, отделяющие сетевую часть от части узла;
- **длина префикса** — число единиц в маске; `/27` означает 27 единиц;
- **адрес сети** — минимальный адрес блока, у которого все биты части узла равны нулю;
- **часть узла** (host part) — биты, различающие адреса внутри блока.

### Пример подсети, начинающейся не с нуля

Возьмём адрес `192.168.1.77/27`. В части узла остаётся `32 - 27 = 5` бит, поэтому размер блока равен `2⁵ = 32` адресам. Границы блоков в последнем октете идут с шагом 32:

```text
0, 32, 64, 96, 128, 160, 192, 224
```

Адрес 77 попадает в диапазон `64..95`, следовательно:

```text
сеть:         192.168.1.64/27
первый узел:  192.168.1.65
последний узел: 192.168.1.94
broadcast:    192.168.1.95
```

В обычной IPv4-подсети адрес со всеми нулями в host part обозначает сеть, а адрес со всеми единицами — направленный broadcast. Поэтому из 32 адресов здесь традиционно доступны 30 адресов узлов. У правила есть важные исключения: `/31` используют на point-to-point-линиях без network/broadcast-потерь, а `/32` описывает ровно один адрес.

### Что означают `/0`, `/1` и `/32`

- `0.0.0.0/0` фиксирует ноль бит, поэтому совпадает с любым IPv4-адресом. Нулевой адрес слева — канонический адрес этого блока: все незафиксированные биты обнулены. Это буквально вся IPv4-адресная область.
- `0.0.0.0/1` фиксирует первый бит как `0` и покрывает адреса `0.0.0.0`–`127.255.255.255`.
- `128.0.0.0/1` фиксирует первый бит как `1` и покрывает вторую половину адресов. Вместе две записи `/1` покрывают весь IPv4, но обе специфичнее существующего маршрута `/0`.
- `10.8.0.4/32` фиксирует все 32 бита. Маска равна `255.255.255.255`, а маршрут совпадает только с одним адресом.

Пара `/1` часто используется VPN-клиентом как аккуратный способ перекрыть существующий default route, не удаляя его. По правилу наиболее длинного префикса `/1` выигрывает у `/0`, а исходный маршрут остаётся в таблице и продолжает быть доступен для более специальных исключений.

### Специальные диапазоны

Не всякий непубличный адрес является «частным», и последние адреса подсети не имеют отношения к multicast.

| Диапазон | Назначение |
|---|---|
| `10.0.0.0/8` | частные сети |
| `172.16.0.0/12` | частные сети |
| `192.168.0.0/16` | частные сети |
| `127.0.0.0/8` | loopback: трафик остаётся на том же хосте |
| `169.254.0.0/16` | IPv4 link-local: связь в локальном сегменте без настроенного адреса |
| `224.0.0.0/4` | IPv4 multicast: адреса групп получателей |
| `255.255.255.255/32` | ограниченный broadcast в локальном сегменте |

Частные адреса из RFC 1918 не маршрутизируются в глобальном Интернете и обычно выходят наружу через NAT. Loopback — отдельная семантика: `127.0.0.1` не означает домашний роутер и никогда не должен уйти на сетевую карту. Link-local применяется только в пределах непосредственно подключённого канала. Multicast обозначает группу подписчиков; соответствие multicast-адреса получателям поддерживается отдельными механизмами, а не выбором «последнего адреса подсети».

## Как читать таблицу маршрутизации

Записи вида

```text
default via 192.168.1.1 dev wlan0 proto dhcp metric 600
10.8.0.0/24 dev tun0 scope link
203.0.113.10 via 192.168.1.1 dev wlan0
```

похожи и на конфигурацию, и на вывод утилиты, потому что Linux-команда `ip route` использует почти один синтаксис для просмотра и изменения маршрутов. `ip route show` выводит таблицу, а `ip route add ...` и `ip route del ...` меняют её.

Первую строку можно прочитать как предложение: «для адресов, не совпавших с более конкретным маршрутом (`default`), передать пакет следующему маршрутизатору `192.168.1.1` (`via`) через интерфейс Wi-Fi `wlan0` (`dev`); маршрут получен по DHCP (`proto dhcp`), его метрика — 600».

Основные поля означают следующее:

- **destination prefix** — диапазон адресов назначения, например `10.8.0.0/24`;
- **next hop** или **gateway** — соседний маршрутизатор, которому следует передать пакет;
- **interface** (`dev`) — локальный выход: `wlan0`, `eth0`, `tun0`, `lo`;
- **directly connected route** (`scope link`) — адрес назначения доступен в том же канале, промежуточный gateway не нужен;
- **default route** — маршрут `0.0.0.0/0`, используемый, если нет более специального;
- **metric** — стоимость или предпочтение среди маршрутов с одинаковым префиксом: при прочих равных выигрывает маршрут с меньшей метрикой.

Метрика не сравнивается между всеми строками сразу. Сначала ядро выбирает маршрут с **самым длинным совпавшим префиксом** (longest prefix match), а уже затем разрешает равенства с учётом метрики, типа маршрута, policy rules и других атрибутов.

```text
0.0.0.0/0  via 192.168.1.1 dev wlan0 metric 600
8.8.8.0/24 dev tun0 metric 100
8.8.8.8/32 via 192.168.1.1 dev wlan0 metric 900
```

Для `8.8.8.8` победит `/32`, хотя его метрика больше: 32 совпавших бита специфичнее 24 и 0. Для `8.8.8.9` победит `/24`, для `1.1.1.1` — default route.

### Gateway и соседний канал

Gateway — не свойство хоста «вообще», а часть конкретного маршрута. У ноутбука могут одновременно быть gateway Wi-Fi, gateway Ethernet и маршруты через VPN. Default gateway — лишь gateway у маршрута по умолчанию.

Домашний адрес gateway часто приходит вместе с IP-адресом, префиксом и DNS-серверами по DHCP. IPv4-клиент, ещё не имея полноценной конфигурации, обменивается широковещательными DHCP-сообщениями по UDP (клиентский порт 68, серверный 67); сервер предлагает lease и параметры сети. После этого ОС создаёт адрес интерфейса и маршруты. Статическая конфигурация или VPN-клиент могут добавить другие gateway и правила позднее.

Запись `via 192.168.1.1 dev wlan0` допустима, только если `192.168.1.1` достижим через `wlan0` как сосед. Иначе для доставки к gateway потребовался бы ещё один неразрешимый маршрут.

### Маршрут до VPN-сервера

Предположим, публичный адрес VPN-сервера — `203.0.113.10`, а после подключения весь трафик должен идти в `tun0`:

```text
default dev tun0
```

VPN-клиенту всё ещё нужно отправлять внешние пакеты на `203.0.113.10` через Wi-Fi. Без исключения ядро направит их обратно в `tun0`; клиент прочитает пакет, снова попытается завернуть его для того же сервера и получит routing loop.

Решение — более специфичный маршрут к endpoint:

```text
203.0.113.10/32 via 192.168.1.1 dev wlan0
```

На Android ту же задачу решает `VpnService.protect()` для сокета туннеля: система исключает его из VPN-маршрута. На других платформах применяются host route, привязка сокета к физическому интерфейсу, policy routing или комбинация этих механизмов.

## Full tunnel, split tunnel и policy routing

**Full tunnel** означает, что политика направляет через VPN весь трафик, кроме технически необходимых исключений. Концептуальная запись — `0.0.0.0/0 dev tun0`; на практике клиент может установить два маршрута `/1`, отдельные правила для IPv6 и исключение до VPN endpoint.

**Split tunnel** — не один протокол, а общая концепция разделения трафика между разными путями. Делить можно по адресам, приложениям, пользователям, доменам или иным признакам. В VPN один путь проходит через tunnel interface, другой — в обход него. В примере с браузером, выбирающим прямое соединение либо proxy по доменному правилу, виртуального IP-туннеля нет: точнее называть это split routing или split proxying, хотя пользовательские интерфейсы нередко используют более широкое название split tunneling.

Простейший IP-based split tunnel реализуется маршрутами:

```text
10.0.0.0/8 dev tun0       # корпоративные адреса через VPN
default via 192.168.1.1   # остальное напрямую
```

Обратная политика задаёт default через VPN и более специальные исключения для локальной сети. Перекрывающиеся диапазоны не являются ошибкой сами по себе: longest prefix match позволяет общему правилу иметь исключения.

Обычная таблица отвечает в основном на вопрос «куда отправить пакет с адресом назначения X?». **Policy routing** сначала выбирает таблицу по дополнительным признакам, а затем применяет в ней обычный поиск маршрута:

```{mermaid}
flowchart LR
    Packet[Пакет] --> Rules[Policy rules]
    Rules -->|source, mark,<br/>interface, user| Table[Выбранная таблица]
    Table --> LPM[Longest prefix match]
    LPM --> Interface[Gateway и интерфейс]
```

В Linux `ip rule show` выводит правила, а `ip rule add` и `ip rule del` их меняют. Например, firewall может поставить пакету метку `fwmark 0x1`, правило направит такие пакеты в таблицу 100, а в таблице 100 default route будет вести в VPN:

```bash
ip rule add fwmark 0x1 lookup 100
ip route add default dev tun0 table 100
```

Жизненный пример — два VPN одновременно: рабочие процессы получают одну метку и идут через корпоративный туннель, браузер — другую и идёт через личный, остальной трафик использует основную таблицу. VPN-приложение может само управлять этими объектами через системные API — на Linux обычно через netlink — либо запускать внешние команды. Это не просто инструкция пользователю: полноценный клиент устанавливает и откатывает правила при подключении, переподключении и смене сети.

### Разделение по приложениям

Пакет сам по себе не всегда хранит идентичность процесса, поэтому per-app split tunneling платформенно специфичен.

- На Android `VpnService.Builder` принимает allowlist или denylist пакетов приложений до создания TUN-интерфейса. Для изменения списка интерфейс обычно создают заново.
- Windows Filtering Platform (WFP) умеет классифицировать трафик на нескольких слоях стека, в том числе с учётом приложения, и применять разрешение, блокировку, маркировку или перенаправление. Маршруты и параметры интерфейсов меняются через отдельные сетевые API.
- На Linux трафик можно связать с cgroup, UID или mark с помощью firewall/cgroup-механизмов, затем выбрать таблицу через `ip rule`. Простое правило по PID ненадёжно: процессы завершаются, сокеты наследуются, а часть трафика создают системные службы.
- В экосистеме Apple packet tunnel строится через Network Extension; per-app VPN тесно связан с системными и управляемыми политиками, а доступные режимы зависят от платформы и entitlement приложения.

## От локального маршрута к Интернету: Ethernet, ARP и BGP

Маршрутизация уровня L3 выбирает **следующий IP-hop**, а не физический путь до конечного сайта. Если next hop — домашний роутер `192.168.1.1`, сетевой карте ещё нужно понять, в какой Ethernet-кадр поместить IP-пакет.

### ARP и локальный сегмент

В IPv4 соответствие «соседний IP → MAC-адрес» строит ARP (Address Resolution Protocol). Если записи нет в neighbor cache, хост отправляет широковещательный вопрос примерно такого смысла: «кто владеет `192.168.1.1`?» Владелец отвечает своим MAC-адресом, и ОС на ограниченное время сохраняет соответствие.

```{mermaid}
sequenceDiagram
    autonumber
    participant Host as Ноутбук 192.168.1.37
    participant LAN as Ethernet/Wi-Fi сегмент
    participant GW as Роутер 192.168.1.1

    Host->>LAN: ARP broadcast: кто имеет 192.168.1.1?
    LAN->>GW: Кадр получают участники broadcast domain
    GW-->>Host: ARP reply: 192.168.1.1 = MAC aa:bb:cc:dd:ee:ff
    Host->>Host: Сохранить запись в neighbor cache
    Host->>GW: Ethernet frame с IP-пакетом внутри
```

Хост делает ARP не для адреса далёкого сайта, а для next hop. Если получатель находится в той же подсети, next hop совпадает с самим получателем. Если в другой — кадр адресуется MAC-адресу gateway, а IP-заголовок по-прежнему содержит конечный IP сайта.

**Коммутатор** пересылает Ethernet-кадры внутри L2-сегмента по MAC-адресам и обучается, за какими портами они находятся. **Маршрутизатор** соединяет разные IP-сети, снимает входной L2-заголовок, выбирает следующий маршрут и строит новый L2-заголовок для следующего канала. Broadcast domain обычно ограничен маршрутизатором или VLAN; ARP через весь Интернет не распространяется.

Если два компьютера соединены напрямую или подключены к одному L2-сегменту, они могут разрешить адреса друг друга через ARP. Wi-Fi-точка доступа и Ethernet-коммутатор создают похожую логическую связанность, хотя физическая среда различается. В IPv6 эту роль выполняет Neighbor Discovery Protocol (NDP) поверх ICMPv6.

Виртуальная сеть может быть L3 или L2. TUN переносит IP-пакеты, поэтому внутри такого туннеля ARP обычно нет. TAP переносит Ethernet-кадры и способен протянуть ARP и broadcast через туннель. На физических интерфейсах клиента и сервера neighbor discovery всё равно требуется для доставки **внешних** пакетов до соседних роутеров.

### Как маршруты появляются между провайдерами

Таблица на ноутбуке и протокол BGP решают связанные, но разные задачи. Ноутбук обычно знает несколько локальных маршрутов и default gateway. Провайдерские маршрутизаторы должны решить, в сторону какой сети отправлять пакеты для сотен тысяч глобальных префиксов.

Интернет состоит из автономных систем (Autonomous Systems, AS): сетей провайдеров, облаков и крупных организаций с единой политикой маршрутизации. BGP (Border Gateway Protocol) распространяет между ними объявления вида «префикс `203.0.113.0/24` достижим через AS64500». Маршрутизатор применяет локальную политику, длину AS path и другие атрибуты, выбирает лучший путь и устанавливает его в рабочую таблицу пересылки.

Ошибочное объявление слишком широкого или чужого префикса может перетянуть трафик, потому что более специфичный маршрут часто выигрывает. Так небольшая сеть способна вызвать крупный сбой: соседи приняли некорректный анонс и распространили его дальше.

Защита стала лучше, но не абсолютна. Операторы применяют prefix-фильтры, лимиты количества маршрутов, проверку ожидаемых соседей и RPKI Route Origin Validation. В RPKI владелец адресного блока публикует подписанный ROA — разрешение конкретной AS анонсировать префикс. Сеть-получатель может отвергать объявления с недопустимым origin. Такая проверка защищает origin префикса, но сама по себе не доказывает корректность всего AS path; кроме того, результат зависит от полноты публикации ROA и применения фильтров операторами.

## TUN, TAP и связь с VPN-процессом

Виртуальный интерфейс выглядит для сетевого стека как сетевой адаптер, но вместо радиомодуля или Ethernet-контроллера за ним находится программный канал.

**TUN** работает на L3: читатель получает IP-пакеты. **TAP** работает на L2: читатель получает целые Ethernet-кадры с MAC-адресами. Большинству routed VPN нужен TUN: он переносит IPv4/IPv6 без лишнего L2 broadcast и проще вписывается в мобильные API.

На Linux общий драйвер TUN/TAP создаёт сетевой интерфейс и файловый дескриптор через clone device `/dev/net/tun`. Когда таблица маршрутизации выбирает `tun0`, ядро кладёт исходящий IP-пакет в очередь; VPN-процесс получает его вызовом `read()`. После получения внешнего пакета процесс расшифровывает внутренний IP-пакет и возвращает его в сетевой стек вызовом `write()` на том же дескрипторе.

`/dev/net/tun` — не общий файл, из которого любое приложение может читать пакеты всех туннелей. Процесс открывает clone device и через `ioctl(TUNSETIFF)` создаёт интерфейс либо присоединяется к разрешённой ему очереди. Создание и настройка интерфейса требуют `CAP_NET_ADMIN`; у persistent TUN/TAP можно назначить владельца или группу и разрешить им повторное подключение. Полученный file descriptor принадлежит процессу и недоступен постороннему процессу, пока его явно не унаследовали или не передали через межпроцессное взаимодействие. Мобильные и desktop VPN API обеспечивают ту же границу своими разрешениями, entitlement и закрытыми handles.

Направления здесь названы относительно пользовательского трафика, а `read()` и `write()` — относительно VPN-процесса. Пакет, который ядро собирается **отправить** через `tun0`, появляется в TUN-очереди, поэтому процесс забирает его вызовом `read()`. Расшифрованный пакет с внешней сети процесс, наоборот, передаёт ядру вызовом `write()`; для сетевого стека он выглядит как пакет, **принятый** интерфейсом `tun0`.

Исходящий путь использует `read()`:


Граница реализации зависит от протокола и платформы. OpenVPN и userspace-реализации WireGuard читают виртуальный интерфейс из userspace; Linux WireGuard может выполнять туннелирование в kernel module и показываться как обычный сетевой интерфейс без userspace-цикла на каждый пакет. Android возвращает VPN-приложению `ParcelFileDescriptor`; Apple даёт `NEPacketTunnelFlow`; Windows-клиенты используют виртуальный адаптер и драйверный интерфейс, например семейство TUN-драйверов. Во всех случаях сохраняется одна модель: ОС направляет IP-пакеты в виртуальный интерфейс, а реализация VPN превращает их во внешний защищённый обмен.

TAP полезен, когда нужно объединить удалённые узлы в один Ethernet-сегмент: перенести не-IP протокол, DHCP broadcast или приложение, зависящее от L2. Цена — broadcast- и multicast-шум, более крупные заголовки, сложная борьба с петлями и плохая масштабируемость. Поэтому routed TUN обычно предпочтительнее, особенно на мобильных устройствах.

## VPN-сервер как маршрутизатор: forwarding, NAT и conntrack

После расшифрования сервер получает пакет:

```text
src = 10.8.0.2
dst = 8.8.8.8
```

Адрес назначения не принадлежит самому VPN-серверу. Сервер должен действовать как маршрутизатор: принять пакет на tunnel-интерфейсе, выполнить routing lookup и **переслать** (forward) его через выбранный таблицей маршрутизации внешний интерфейс. В Linux пересылку IPv4 разрешает параметр ядра `net.ipv4.ip_forward`. Текущее значение доступно в `/proc/sys/net/ipv4/ip_forward`; временно включить его можно командой `sysctl -w net.ipv4.ip_forward=1`, а постоянное значение задают в файле `/etc/sysctl.d/*.conf`. Firewall отдельно должен разрешить соответствующий транзит.

Forwarding относится не к «пересылке интерфейса», а к судьбе пакета. Пакет, адресованный одному из локальных адресов хоста, проходит к локальному процессу — это не только loopback, но и адреса `eth0`, `tun0`, а также некоторые broadcast/multicast-пакеты, на которые подписан хост. Пакет с нелокальным destination является транзитным: ядро ищет для него маршрут и при разрешённом forwarding передаёт из входного интерфейса в указанный этим маршрутом выходной.

### Зачем нужен NAT

Частный адрес `10.8.0.2` из RFC 1918 не маршрутизируется в публичном Интернете. При выходе клиента в Интернет VPN-сервер меняет source на свой публичный адрес. Это **SNAT** (Source NAT):

```text
до:    10.8.0.2:53000       -> 8.8.8.8:53
после: 203.0.113.50:62001   -> 8.8.8.8:53
```

Изменение source port называют port translation или PAT. Оно позволяет различать одновременные потоки нескольких клиентов, даже если исходные порты совпали.

Ядро сохраняет состояние потока в conntrack. Когда ответ приходит на `203.0.113.50:62001`, состояние подсказывает обратное преобразование к `10.8.0.2:53000`. Stateful firewall использует ту же модель потоков, чтобы разрешать ответы на уже установленные соединения, не открывая произвольные входящие пакеты.

```{mermaid}
sequenceDiagram
    autonumber
    participant C as VPN-клиент 10.8.0.2
    participant V as VPN-сервер 203.0.113.50
    participant N as Интернет
    participant D as Сервер 8.8.8.8

    C->>V: Зашифрованный внешний пакет
    V->>V: Decrypt: 10.8.0.2:53000 → 8.8.8.8:53
    V->>V: FORWARD + SNAT<br/>203.0.113.50:62001 → 8.8.8.8:53
    V->>N: Пакет с публичным source
    N->>D: Маршрутизация по Интернету
    D-->>N: 8.8.8.8:53 → 203.0.113.50:62001
    N-->>V: Ответ VPN-серверу
    V->>V: Conntrack + reverse NAT<br/>8.8.8.8:53 → 10.8.0.2:53000
    V-->>C: Зашифрованный ответ
```

`MASQUERADE` — действие SNAT на самом VPN-сервере. В правиле `iptables -t nat -A POSTROUTING -s 10.8.0.0/24 -o eth0 -j MASQUERADE` ядро берёт текущий IP **серверного** интерфейса `eth0` и записывает его в source выходящего пакета. Правило продолжает работать, если этот адрес серверу выдали динамически и он изменился.

Если у `eth0` закреплён адрес `203.0.113.50`, ту же подмену можно выразить явно: `iptables -t nat -A POSTROUTING -s 10.8.0.0/24 -o eth0 -j SNAT --to-source 203.0.113.50`. Здесь `SNAT --to-source` — синтаксис target и его параметра в команде `iptables`, а не отдельная настройка VPN.

NAT не нужен в сети, где маршрутизаторы знают обратный путь к `10.8.0.0/24` через VPN-сервер. Реальный пример — site-to-site VPN между двумя офисами: роутер второго офиса содержит маршрут к удалённой подсети через VPN-шлюз, поэтому ответы возвращаются к исходным адресам без подмены. Это сохраняет адрес клиента для журналов и сетевых политик. Публичные маршрутизаторы не принимают маршруты к RFC 1918, поэтому для обычного выхода VPN-клиента в Интернет применяется SNAT.

**DNAT** меняет destination. Это тот же механизм, который домашние роутеры называют «пробросом портов»: публичный `203.0.113.50:443` перенаправляется на внутренний web-сервер `10.0.0.20:8443`. Обратный трафик снова должен пройти через узел NAT, иначе преобразование окажется асимметричным.

### Netfilter без заклинаний

Netfilter — набор hook points в сетевом стеке Linux. `nftables` — современный интерфейс настройки правил; `iptables` — старый, но всё ещё распространённый интерфейс. Имена `INPUT`, `OUTPUT` и `FORWARD` обозначают цепочки по судьбе пакета:

```{mermaid}
flowchart TD
    In[Пакет с интерфейса] --> Pre[PREROUTING]
    Pre --> PreNat[DNAT / reverse NAT<br/>если применимо]
    PreNat --> Route{Destination<br/>локальный?}
    Route -->|да| Input[INPUT]
    Input --> Local[Локальный сокет]
    Route -->|нет| Forward[FORWARD]
    Forward --> Post[POSTROUTING]
    Post --> PostNat[SNAT / MASQUERADE<br/>если применимо]
    PostNat --> OutIf[Выходной интерфейс]

    Process[Локальный процесс] --> Output[OUTPUT]
    Output --> OutRoute[Routing]
    OutRoute --> Post
```

Таблица `filter` решает, разрешить или отбросить трафик. Таблица `nat` задаёт преобразования адресов, обычно для первого пакета потока; последующие пакеты следуют состоянию conntrack. `ESTABLISHED` означает пакет известного двустороннего потока. `RELATED` — новый поток или служебный пакет, связанный с известным, например ICMP-ошибка о ранее отправленном пакете.

Минимальная серверная конфигурация в синтаксисе `iptables` может выглядеть так:

```bash
sysctl -w net.ipv4.ip_forward=1

iptables -A FORWARD -i tun0 -o eth0 \
  -s 10.8.0.0/24 -m conntrack --ctstate NEW,ESTABLISHED \
  -j ACCEPT

iptables -A FORWARD -i eth0 -o tun0 \
  -d 10.8.0.0/24 -m conntrack --ctstate ESTABLISHED,RELATED \
  -j ACCEPT

iptables -t nat -A POSTROUTING -s 10.8.0.0/24 \
  -o eth0 -j MASQUERADE
```

Второе правило `FORWARD` видит пакет `-i eth0 -o tun0 -d 10.8.0.0/24` уже **после обратного NAT**. По проводу ответ приходит на `eth0` с destination `203.0.113.50:62001`. В `PREROUTING` conntrack восстанавливает `10.8.0.2:53000`, затем новый routing lookup выбирает `tun0`. Поэтому пакет с private destination не возник во внешней подсети: адрес переписан внутри VPN-сервера до проверки цепочки `FORWARD`.

Здесь `-A` добавляет правило в цепочку, `-i` и `-o` задают входной и выходной интерфейсы, `-s`/`-d` — source/destination, `-m conntrack` подключает проверку состояния, `--ctstate` перечисляет допустимые состояния, `-j ACCEPT` выбирает действие. В последнем правиле `-t nat` выбирает NAT-таблицу, а `POSTROUTING` означает «после выбора выходного маршрута».

Это пример модели, а не универсальный production-скрипт: нужны отдельные правила для IPv6, защита входа на сам сервер, корректное удаление правил и учёт существующей политики.

## KillSwitch как инвариант маршрутизации и firewall

KillSwitch должен поддерживать инвариант: пользовательский трафик либо идёт через активный защищённый путь, либо блокируется. Простого удаления default route недостаточно — система может восстановить маршрут через DHCP, выбрать IPv6 или другой интерфейс. Поэтому надёжная реализация использует firewall и устанавливает запрет **до** переключения маршрутов.

Обычно разрешаются:

- трафик внутри tunnel-интерфейса;
- внешний сокет до текущего VPN endpoint через физическую сеть;
- локальные служебные пакеты, необходимые для поддержания сети;
- явно выбранный доступ к LAN;
- loopback и необходимые взаимодействия между локальными процессами.

| Сценарий | Что ломается | Какой инвариант нужен |
|---|---|---|
| Переподключение | Между удалением старого route и созданием нового пакет уходит напрямую | deny-policy устанавливается заранее и снимается только после готовности туннеля |
| DNS | Резолвер продолжает спрашивать DNS провайдера | разрешён только DNS через туннель или доверенный локальный proxy; настройки DNS и firewall меняются согласованно |
| VPN endpoint | Запрет блокирует сам внешний туннель | точечное исключение для адреса/порта endpoint, обновляемое при смене адреса |
| LAN | Общий запрет убирает принтеры и локальные сервисы | явные маршруты и firewall-исключения для доверенных локальных префиксов |
| DHCP и IPv6 RA (Router Advertisement) | Интерфейс теряет lease или IPv6-конфигурацию | разрешены только необходимые link-local/broadcast control messages |
| Wi-Fi → Ethernet | Правило привязано к старому интерфейсу | политика пересчитывается при изменении сети и не допускает временного обхода |
| Sleep/resume | ОС восстановила маршруты и DNS раньше VPN | состояние после пробуждения проверяется заново до разблокировки трафика |

Разрешение LAN — осознанный компромисс: оно сохраняет локальные устройства, но позволяет трафику к этим префиксам идти незашифрованным. На незнакомой Wi-Fi-сети такое исключение может быть нежелательно.

## MTU, фрагментация, PMTUD и MSS

**MTU** расшифровывается как Maximum Transmission Unit — максимальный размер сетевого пакета, который интерфейс способен передать одним блоком без фрагментации на этом канале. Для Ethernet значение 1500 обычно означает максимальный размер IP-пакета внутри Ethernet-кадра; Ethernet-заголовок в эти 1500 байт не входит.

VPN добавляет внешние заголовки. Внутренний TCP-пакет нельзя оставить размером 1500 и затем безнаказанно добавить outer IP, UDP и заголовок VPN: внешний IP-пакет станет больше MTU физического пути.

```{mermaid}
flowchart TB
    subgraph Frame[Ethernet frame]
        direction TB
        Ethernet[Ethernet header]

        subgraph Outer[Outer IP packet ≤ physical MTU]
            direction TB
            OuterIP[Outer IP header]
            UDP[UDP header]
            VPN[VPN header + authentication data]

            subgraph Inner[Encrypted inner IP packet]
                direction TB
                InnerIP[Inner IP header]
                Transport[TCP/UDP header]
                Data[Application data]
                InnerIP --> Transport --> Data
            end

            OuterIP --> UDP --> VPN --> Inner
        end

        Ethernet --> Outer
    end
```

Поэтому MTU виртуального интерфейса уменьшают на размер внешнего overhead с запасом на используемые семейства адресов и расширения протокола:

```text
inner MTU + outer headers <= path MTU
```

### Что такое IP-фрагментация

Фрагментация делит слишком большой IP-пакет на несколько IP-фрагментов, которые получатель собирает обратно. Это допустимый механизм, но плохой нормальный режим для туннеля:

- потеря одного фрагмента делает бесполезной всю исходную датаграмму;
- reassembly потребляет память и состояние только на конечном узле;
- middlebox может отбрасывать фрагменты или обрабатывать их иначе;
- дополнительные размеры и последовательности пакетов ухудшают производительность и могут образовать заметный fingerprint.

В IPv4 промежуточный маршрутизатор может фрагментировать пакет, если бит **DF** (Don't Fragment) не установлен. При DF=1 маршрутизатор отбрасывает слишком большой пакет и должен вернуть ICMP `Destination Unreachable, Fragmentation Needed` с допустимым MTU.

В IPv6 маршрутизаторы не фрагментируют транзитные пакеты. Они отбрасывают слишком большой пакет и отправляют ICMPv6 `Packet Too Big`; фрагментировать при необходимости может только исходный узел с IPv6 Fragment extension header.

**ICMP** (Internet Control Message Protocol) — служебный протокол сетевого уровня, переносящий ошибки и диагностические сообщения внутри IP. `ping` использует ICMP Echo, а PMTUD — сообщения о слишком большом пакете. **IGMP** (Internet Group Management Protocol) тоже находится рядом с IP, но управляет членством IPv4-хостов в multicast-группах и к MTU не относится.

### Как работает Path MTU Discovery

Path MTU (PMTU) — минимальный link MTU среди всех звеньев текущего пути. Path MTU Discovery (PMTUD) — процесс, в котором отправитель учится не превышать это значение.

Для классического PMTUD отправитель посылает пакеты, не допускающие фрагментацию. Если узкое звено не может их передать, маршрутизатор сообщает меньший MTU через ICMP/ICMPv6, после чего источник уменьшает размер следующих пакетов. Это происходит не только во время handshake: оценка хранится для маршрута и может обновляться по мере передачи данных. PMTU не распространяется в TCP-заголовках как готовое «минимальное число от всех роутеров».

Если firewall блокирует ICMP `Fragmentation Needed` или `Packet Too Big`, возникает PMTUD black hole: маленькие пакеты проходят, большие молча исчезают. TCP-соединение может установиться, но передача сертификата TLS или крупного ответа зависнет.

PLPMTUD (Packetization Layer PMTUD) ищет рабочий размер пробными пакетами на транспортном или прикладном слое и не полагается только на ICMP. Он особенно полезен там, где ICMP фильтруется.

**MSS** (Maximum Segment Size) — максимальный объём TCP payload в одном сегменте, который сторона объявляет в SYN. Обычно MSS вычисляется из доступного IP MTU минус IP- и TCP-заголовки. **MSS clamping** на роутере или VPN-шлюзе уменьшает объявляемый MSS в проходящих SYN, чтобы TCP-пиры сразу формировали сегменты, помещающиеся в туннель. Это помогает TCP, но не исправляет произвольные крупные UDP-датаграммы.

В obfuscation-протоколах **junk packet** — искусственная датаграмма без пользовательской полезной нагрузки, добавленная для изменения наблюдаемой последовательности размеров и времён. Если её размер превышает PMTU, она фрагментируется или теряется. Тогда попытка скрыть fingerprint способна создать новый характерный признак либо вообще сломать handshake.

Типичный диагностический набор:

```bash
ip link show tun0          # проверить MTU интерфейса
ping -M do -s 1372 host    # IPv4: проба с DF и выбранным payload
tracepath host             # оценка PMTU по пути
tcpdump -ni any icmp or icmp6
```

Точный размер для `ping` должен учитывать IP- и ICMP-заголовки, поэтому число payload нельзя напрямую считать MTU.

## TCP и UDP как внешний транспорт VPN

Полное устройство TCP заслуживает отдельного материала. Для VPN достаточно держать причинную модель: TCP создаёт упорядоченный надёжный поток байтов, нумерует байты sequence numbers, подтверждает полученное ACK-ами и повторяет потерянное. Receive window ограничивает объём данных, который готов принять получатель; congestion window ограничивает нагрузку на сеть. SYN открывает соединение, FIN закрывает его согласованно, RST обрывает, а `TIME_WAIT` защищает новое соединение от запоздалых сегментов старого.

### Почему TCP-over-TCP ведёт себя плохо

Пусть обычное HTTPS-соединение TCP помещено внутрь VPN, который сам использует один внешний TCP-поток:

```text
inner TCP: browser → website
outer TCP: VPN client → VPN server
```

При потере внешнего сегмента outer TCP не отдаёт следующие байты VPN-серверу, пока не восстановит пропуск: порядок потока обязателен. В одном таком пропуске застревают пакеты всех внутренних соединений — head-of-line blocking. Внутренние TCP-пиры тем временем не получают ACK и тоже запускают свои retransmission timers и congestion control. Повторно переданный внутренний сегмент становится ещё одними байтами того же внешнего потока, который уже пытается восстановить старые байты. Два управляющих контура реагируют на одну потерю независимо, создают лишние повторы и резко уменьшают окна.

TCP-транспорт остаётся полезным fallback в сетях, где UDP заблокирован, но это компромисс, а не равноценная замена UDP.

### Что именно даёт UDP

UDP сохраняет границы датаграмм и добавляет порты с checksum, но не обещает доставку, порядок, устранение дубликатов или congestion control. Вызов `connect()` для UDP не создаёт сетевого handshake: ядро сохраняет default peer для этого сокета, после чего `send()` можно вызывать без адреса назначения, а входящие датаграммы доставляются от выбранного peer.

Внешняя UDP-датаграмма идёт между VPN-клиентом и VPN-сервером. Её payload содержит либо служебное сообщение самого VPN-протокола — например, handshake WireGuard, — либо зашифрованный внутренний IP-пакет клиента. WireGuard повторяет handshake-сообщение, если не получил ожидаемый ответ, но не подтверждает и не повторяет каждый data packet: надёжность внутреннего TCP остаётся внутреннему TCP, а realtime UDP-приложение может предпочесть свежий пакет запоздалому повтору.

NAT и stateful firewall всё равно хранят временное UDP-состояние по tuple адресов и портов. Если долго нет пакетов, mapping исчезает, и входящие датаграммы к старому внешнему порту больше не доходят. Keepalive — маленький периодический пакет, обновляющий это состояние.

В WireGuard параметр `PersistentKeepalive = 25` означает интервал около 25 секунд, а не количество попыток. Он нужен peer за NAT, который должен оставаться доступным для входящего трафика после простоя. Без такой необходимости keepalive можно не включать: обычный исходящий трафик сам обновляет mapping.

**UDP hole punching** использует тот же эффект. Каждый из двух клиентов за NAT сначала отправляет UDP наружу, создавая mapping; координационный сервер сообщает им наблюдаемые публичные endpoint. Затем клиенты пробуют слать друг другу. Метод зависит от поведения обоих NAT и firewall и не гарантирован, поэтому системы вроде WebRTC имеют relay fallback.

## DNS в системе с VPN

Подробная цепочка `getaddrinfo()` → системный resolver → DNS-сервер разобрана в отдельной статье [про WebSocket, HTTP и TLS](websocket-http-tls.md). Здесь важна граница: маршрутизация IP-пакетов начинается **после** того, как имя уже превратилось в адрес, но сам DNS-запрос также является сетевым трафиком и может пойти через другой интерфейс.

Упрощённый путь:

```{mermaid}
flowchart LR
    App[Приложение] --> Stub[Stub / system resolver]
    Stub --> Policy[Кеш и DNS routing policy]
    Policy --> Recursive[Recursive DNS resolver]
    Recursive --> Authoritative[Authoritative DNS servers]
```

**DNS провайдера** (ISP DNS) — recursive resolver, адрес которого клиент получает от домашнего роутера или провайдера через DHCP, IPv6 Router Advertisement/DHCPv6 либо из конфигурации подключения.

### DNS leak и split DNS

DNS leak возникает, когда полезный трафик идёт через VPN, а запрос имени — напрямую к resolver провайдера. Провайдер тогда видит запрошенные домены и время запросов, хотя последующее соединение скрыто внутри туннеля. Шифрованные DoH/DoT скрывают имя от промежуточной сети, но выбранный DoH/DoT-провайдер всё равно получает запросы, а само прямое соединение с ним может нарушать политику VPN.

**Split DNS** выбирает resolver по доменному пространству:

```text
*.corp.example → корпоративный DNS через VPN
остальные имена → обычный resolver
```

Реализация различается:

- Linux с `systemd-resolved` поддерживает DNS-серверы и routing domains на отдельных link; NetworkManager может настраивать их для VPN-подключения;
- Windows применяет DNS-настройки интерфейсов и политики разрешения имён, включая NRPT в подходящих сценариях;
- Network Extension на Apple-платформах позволяет packet tunnel задать DNS-серверы и match domains;
- Android `VpnService.Builder.addDnsServer()` задаёт DNS для созданной VPN-сети; сложное разделение по доменам часто требует локального DNS-proxy или системной managed-конфигурации.

### Почему домен нельзя просто записать в IP route

Таблица маршрутизации видит destination IP, но не исходное доменное имя. Domain-based split tunneling поэтому обычно:

1. перехватывает или наблюдает DNS-ответ;
2. извлекает A/AAAA-адреса;
3. временно добавляет маршруты к ним;
4. обновляет записи по TTL и новым ответам.

Механизм динамический, даже если список доменов задан статически. Он остаётся неточным: CDN меняет адреса, один IP обслуживает много доменов, приложение может использовать собственный DoH, а уже открытые соединения переживают DNS-запись. Если решение действительно должно приниматься по имени, proxy прикладного уровня часто естественнее: он получает hostname явно в SOCKS/HTTP-запросе или может учитывать SNI там, где это допустимо.

## Архитектура VPN-протоколов

У любого защищённого туннеля есть две логические задачи:

1. **Handshake/control plane** аутентифицирует peers, согласует параметры и получает временные ключи.
2. **Data plane** шифрует и аутентифицирует переносимые пакеты временными симметричными ключами.

Сообщения обоих уровней становятся payload внешнего UDP- или TCP-сокета между VPN-клиентом и VPN-сервером. Это отдельный слой от TLS внутри пользовательского HTTPS. Пакет браузера может уже содержать TLS ciphertext, а VPN затем зашифрует весь внутренний IP-пакет ещё раз. На VPN-сервере снимается только внешнее шифрование; внутренний TLS заканчивается на сайте.

### WireGuard

Разберём клиент, которому известен публичный endpoint VPN-сервера `203.0.113.10:51820`.

#### Что задано до первого пакета

У интерфейса WireGuard есть собственная пара ключей. Private key хранится только на этом узле; соответствующий public key заранее передают другой стороне. Для server peer клиент хранит:

- public key сервера — его криптографическую идентичность;
- `Endpoint = 203.0.113.10:51820` — внешний IP и UDP-порт, куда посылать зашифрованные датаграммы;
- `AllowedIPs` — внутренние destination prefixes, принадлежащие этому peer;
- при необходимости preshared key и `PersistentKeepalive`.

Это конфигурация, а не результат поиска сервера в сети. Клиентский VPN-менеджер также создаёт интерфейс `wg0`, назначает ему внутренний адрес, например `10.8.0.2`, и добавляет системные маршруты. Он обязан сохранить для внешнего endpoint путь в обход `wg0` — через host route или policy routing с mark, — иначе UDP-пакеты handshake попадут в routing loop.

#### Исходящий пакет и выбор peer

Приложение отправляет данные сайту `8.8.8.8`. Обычная системная routing table выбирает `wg0` и передаёт интерфейсу внутренний IP-пакет:

```text
src = 10.8.0.2
dst = 8.8.8.8
```

Затем уже WireGuard ищет peer, чей `AllowedIPs` наиболее длинным префиксом совпадает с `8.8.8.8`. Если у server peer указано `0.0.0.0/0`, пакет выбирает его. При нескольких peers это позволяет одному интерфейсу отправлять разные подсети разным получателям.

Здесь участвуют две таблицы с разными ролями:

1. системная routing table направляет внутренний пакет в `wg0`;
2. cryptokey routing table WireGuard связывает destination этого пакета с public key конкретного peer.

Команда `wg` настраивает вторую таблицу, но не создаёт системный IP route. `wg-quick` по умолчанию строит системные маршруты из `AllowedIPs`; параметр `Table = off` отключает это поведение. Другой VPN-менеджер может настроить маршруты и policy rules своим способом.

#### Handshake внутри UDP

Если действующих session keys ещё нет, WireGuard не может сразу отправить data packet. Он формирует handshake initiation и помещает его в payload UDP-датаграммы к `203.0.113.10:51820`.

Handshake Noise_IK использует заранее известные static public keys и новые ephemeral keys. В первом сообщении клиент передаёт ephemeral public key, защищённое представление своей static identity и timestamp. Сервер проверяет сообщение своим private key и отвечает собственным ephemeral-вкладом. После одного обмена в обе стороны peers получают два симметричных session key: один для направления клиент → сервер, другой для сервер → клиент.

WireGuard не согласует ALPN, сертификаты, версии прикладного протокола или список cipher suites. Криптографический набор и формат сообщений зафиксированы протоколом. Поэтому handshake компактнее TLS-handshake, но выполняет те же необходимые для VPN задачи: аутентифицирует peer, создаёт свежие транспортные ключи и связывает их с текущей сессией.

Если ответ не пришёл, клиент повторяет handshake по своим таймерам. После установления ключей протокол автоматически делает rekey по времени и объёму трафика; ephemeral secrets обеспечивают forward secrecy для завершённых сессий после их удаления.

#### Передача внутреннего пакета

WireGuard шифрует **целиком внутренний IP-пакет** с помощью AEAD и session key. К ciphertext добавляются компактный заголовок transport message, счётчик для nonce/replay protection и authentication tag. Всё это становится payload новой внешней UDP-датаграммы:

```text
outer IP:  client_physical_ip → 203.0.113.10
UDP:       client_port → 51820
payload:   WireGuard header + encrypted inner IP packet + auth tag
```

Если клиент находится за домашним NAT, роутер затем заменит `client_physical_ip:client_port` наблюдаемым сервером публичным endpoint.

В kernel-реализации Linux сам WireGuard-интерфейс владеет UDP-сокетом в ядре. Userspace-реализация создаёт такой сокет в процессе. В обоих случаях внешний routing lookup отправляет датаграмму через физический интерфейс.

Сервер получает UDP payload, по receiver index находит session state, проверяет tag и replay counter, расшифровывает внутренний пакет и проверяет его source по `AllowedIPs` клиентского peer. После этого пакет появляется на серверном WireGuard-интерфейсе и проходит обычные routing, firewall и NAT. Ответ проделывает тот же путь в обратном направлении.

#### Двойная роль `AllowedIPs`

Для исходящего пакета WireGuard ищет peer, чьи `AllowedIPs` наиболее специфично совпадают с destination внутреннего пакета. Для входящего — проверяет, разрешён ли source расшифрованного пакета для аутентифицированного peer. Поэтому поле одновременно похоже на cryptokey routing table и access-control list.

```ini
[Peer]
PublicKey = ...
Endpoint = 203.0.113.10:51820
AllowedIPs = 0.0.0.0/0, ::/0
PersistentKeepalive = 25
```

`AllowedIPs` — конфигурация, которую control software может изменить во время работы; WireGuard не узнаёт новые подсети из Интернета автоматически. Endpoint ведёт себя иначе: корректно аутентифицированный пакет с нового внешнего IP или порта обновляет адрес peer. Эта способность продолжить обмен после смены публичного адреса или NAT mapping называется **roaming** — например, клиент переходит с Wi-Fi на мобильную сеть, сохраняя ту же криптографическую идентичность.

### AmneziaWG как модификация наблюдаемого WireGuard

Обычный WireGuard имеет небольшое число типов сообщений, фиксированные идентификаторы и характерные размеры handshake. Это удобно для реализации, но даёт DPI устойчивую сигнатуру. AmneziaWG сохраняет криптографическую основу WireGuard и меняет видимую транспортную форму.

В актуальной ветке протокола применяются несколько классов преобразований:

- диапазоны значений заголовков вместо фиксированных message type;
- случайные префиксы и padding, меняющие размеры handshake и data packets;
- настраиваемые signature packets перед handshake, имитирующие элементы распространённых UDP-протоколов;
- train из junk packets со случайными размерами, размывающий начало сессии.

Параметры `H1–H4` относятся к заголовкам типов сообщений, `S1–S4` — к добавочной длине, `I1–I5` описывают signature packets, а `Jc`, `Jmin`, `Jmax` — количество и диапазон размеров junk train. Конкретные версии и клиенты поддерживают разные поколения формата, поэтому конфигурация peers должна быть совместима.

Маскировка не меняет фундаментальный вопрос безопасности: ключевой обмен и AEAD остаются задачей WireGuard-ядра. Она решает другую задачу — уменьшает стабильность наблюдаемого fingerprint. Слишком крупный junk packet, некорректная имитация или необычные timing patterns всё равно могут выдать протокол.

### OpenVPN

OpenVPN разделяет control channel и data channel. Control channel использует TLS для аутентификации, согласования параметров и получения ключевого материала. Data channel переносит зашифрованные IP-пакеты отдельными симметричными ключами; это не TLS-сессия браузера внутри туннеля.

OpenVPN может работать поверх UDP или TCP, с TUN или TAP, использовать сертификаты, static key и разные наборы криптографических параметров. `tls-auth` добавляет HMAC-защиту к control packets до дорогой TLS-обработки; `tls-crypt` дополнительно скрывает содержимое control channel. Rekey обновляет data-channel keys без полного разрыва пользовательского трафика.

Гибкость облегчает интеграцию с PKI и legacy-сетями, но увеличивает пространство конфигураций и вероятность несовместимых или слабых настроек. TCP mode помогает пройти сети без UDP ценой TCP-over-TCP для внутреннего TCP.

### Сравнение

| Свойство | WireGuard | AmneziaWG | OpenVPN |
|---|---|---|---|
| Базовая модель | routed L3 VPN | routed L3 VPN на основе WireGuard | L3 TUN или L2 TAP |
| Внешний транспорт | UDP | UDP | UDP или TCP |
| Аутентификация | статические public keys | та же криптографическая модель | TLS, сертификаты/ключи и плагины |
| Согласование криптографии | фиксированный современный набор | как у WireGuard | настраиваемые suites и data ciphers |
| Смена внешнего адреса (roaming) | обновляет endpoint по аутентифицированному пакету | наследует модель WireGuard | зависит от режима и конфигурации |
| Наблюдаемая форма | компактная, но узнаваемая | изменённые headers/sizes/signatures | TLS-подобный control channel, свой data fingerprint |
| Главный компромисс | простота против fingerprintability | маскировка против сложности профиля и остаточных признаков | гибкость против сложности и overhead |

## Proxy и VPN — разные уровни абстракции

VPN принимает внутренние IP-пакеты из виртуального интерфейса, шифрует их и передаёт VPN-шлюзу. Адрес назначения остаётся в заголовке внутреннего пакета, а шлюз после расшифрования маршрутизирует этот пакет дальше.

Proxy работает иначе: клиент сообщает proxy-серверу, с каким destination нужно установить соединение, а proxy создаёт **второе** соединение от своего имени.

### HTTP forward proxy: два TCP-соединения

Допустим, браузер настроен на proxy `proxy.example:3128`, а открыть нужно `https://site.example`.

1. Браузер создаёт TCP-сокет **к proxy-серверу**, не к сайту. Если настроен HTTPS proxy, поверх этого соединения сначала устанавливается TLS между браузером и proxy.
2. По этому соединению браузер отправляет управляющий HTTP-запрос `CONNECT site.example:443 HTTP/1.1`.
3. Proxy-сервер принимает запрос, резолвит `site.example` и создаёт свой отдельный TCP-сокет к `site.example:443`.
4. После успешного подключения proxy отвечает клиенту `200 Connection Established`.
5. С этого момента proxy копирует байты в обе стороны между двумя разными TCP-соединениями. Клиентский сокет всё время остаётся подключённым к proxy; его peer не превращается в сайт.

```{mermaid}
flowchart LR
    Browser[Браузер] -->|TCP A + HTTP CONNECT| Proxy[Forward proxy]
    Proxy -->|TCP B| Site[site.example:443]
    Browser -.->|TLS браузер ↔ сайт<br/>как байты внутри A и B| Site
```

После ответа `200` браузер запускает TLS-handshake с сайтом, а proxy лишь relay'ит его байты. Поэтому end-to-end TLS по-прежнему заканчивается на сайте. Если соединение браузер → proxy также защищено TLS, получается два вложенных защищённых участка с разными endpoints.

Для незашифрованного HTTP метод `CONNECT` не нужен: клиент может отправить proxy запрос с абсолютным URL, а proxy сам сформирует запрос к origin server. Один HTTP/1.1 `CONNECT` создаёт один байтовый туннель к указанному `host:port`; он не позволяет произвольно менять destination внутри уже созданного туннеля.

### SOCKS5 — альтернатива HTTP proxy

SOCKS5 решает ту же базовую задачу отдельным бинарным протоколом. Клиент подключается к SOCKS-серверу, проходит согласование метода аутентификации и отправляет команду `CONNECT` с адресом целевого TCP-сервера. SOCKS-сервер открывает второе соединение и relay'ит байты. Команда `UDP ASSOCIATE` создаёт согласованный relay для UDP-датаграмм; `BIND` применяется в специальных сценариях входящего соединения.

HTTP proxy и SOCKS5 — альтернативные интерфейсы к proxy, а не обязательная пара и не антагонисты. Приложение выбирает поддерживаемый протокол. Их можно соединять в цепочки, но это отдельная конфигурация.

### System proxy, transparent proxy и TUN-to-proxy

**System proxy** означает, что ОС публикует адрес proxy приложениям. Приложение должно прочитать настройку и говорить с proxy по HTTP, SOCKS или поддерживаемому системному API; программа со своим сетевым стеком может её игнорировать.

**Transparent proxy** убирает это требование на клиентской стороне или сетевом шлюзе. Firewall перенаправляет созданный приложением поток локальному proxy-процессу. При `REDIRECT` исходный destination сохраняется в connection metadata, а TPROXY позволяет принять поток с исходными адресами и направить его в proxy через policy routing. Именно локальный proxy-процесс восстанавливает destination, который изначально выбрало приложение, а затем открывает отдельное соединение к удалённому proxy либо сразу к сайту.

Proxy не сводится к переписыванию IP-заголовков как маршрутизатор: он завершает один transport flow и создаёт другой. Удалённый proxy видит запрошенный destination. Содержимое защищает end-to-end TLS приложения; дополнительно клиентский proxy-протокол может шифровать участок до proxy-сервера.

**TUN-to-proxy adapter** — локальный компонент VPN-подобного клиента. ОС направляет ему IP-пакеты через TUN, adapter собирает из них TCP/UDP flows и для каждого создаёт HTTP-, SOCKS-, VLESS- или другой proxy-запрос. Оригинальный IP-пакет не пересылается proxy-серверу целиком: adapter преобразует его в семантику соединения выбранного proxy-протокола. Так приложения, которые ничего не знают о proxy, работают через виртуальный интерфейс, хотя удалённая часть системы остаётся proxy, а не routed IP-VPN.

### VLESS и REALITY

VLESS — лёгкий proxy protocol в экосистеме Xray. Он задаёт аутентификацию клиента и передачу сведений о целевом соединении, но сам по себе не равен IP-VPN и нуждается во внешнем защищённом transport/security layer либо в отдельном режиме шифрования.

REALITY — security/obfuscation layer, который строит правдоподобный TLS-подобный handshake, использует аутентификацию своего клиента и направляет посторонние или не прошедшие проверку подключения к выбранному настоящему TLS-сайту. Идея отличается от изменения UDP-заголовков WireGuard: соединение старается вписаться в экосистему TLS и не выдавать специальный сервис активному probe.

### Почему не туннелировать всё через настоящий HTTPS, WebSocket или QUIC

Так делать можно, и это отдельный полезный класс transports. Настоящий HTTP/WebSocket лучше выдерживает синтаксическую проверку, чем один поддельный ClientHello: после ALPN `h2` действительно идут HTTP/2 frames, а обычный web server способен правдоподобно отвечать на посторонние запросы.

Цена зависит от выбранной инкапсуляции:

- WebSocket поверх HTTPS обычно наследует внешний TCP. Если внутрь положить TCP, возвращается TCP-over-TCP и head-of-line blocking.
- HTTP/2 добавляет framing и multiplexing, но потеря TCP-сегмента останавливает доставку всех streams до восстановления.
- QUIC работает поверх UDP и имеет независимые streams, однако «положить UDP в TLS» напрямую нельзя. Обычный TLS — поток поверх TCP; для датаграмм существуют DTLS, QUIC DATAGRAM и протоколы вроде CONNECT-UDP/MASQUE. Их нужно реализовать как настоящие state machines.
- ALPN `h3` лишь обещает HTTP/3. Если после handshake идёт собственный формат, DPI может заметить несоответствие.
- Полноценный HTTP/3 или MASQUE увеличивает код, overhead, число состояний и зависимость от серверной инфраструктуры. Некоторые сети просто блокируют или ограничивают UDP/QUIC.

Настоящий cover protocol повышает правдоподобие, но не делает flow неотличимым автоматически. Остаются IP endpoint, TLS/QUIC fingerprint клиента, размеры, направления, timing, длительность сессии и активные проверки. Выбор между полной реализацией cover protocol и более лёгкой мимикрией — инженерный компромисс между совместимостью, производительностью и качеством маскировки.

## Что видит DPI

Шифрование скрывает payload и внутренние адреса, но оставляет внешние метаданные. Системы Deep Packet Inspection могут сочетать несколько уровней признаков.

1. **IP reputation.** Destination известен как VPN endpoint или относится к подозрительному hosting range.
2. **Port и транспорт.** Один UDP-порт сам по себе слабый признак, но усиливает остальные.
3. **Protocol signature.** Фиксированные magic bytes, типы сообщений, длины и последовательность handshake.
4. **TLS/QUIC fingerprint.** Набор cipher suites, extensions, groups, ALPN и их порядок в ClientHello. JA3 — исторически популярное свёртывание части этих полей в hash; JA4 — более новое семейство нормализованных fingerprints. Совпадение hash не доказывает протокол, а несовпадение заявленного браузера с реальным профилем повышает подозрение.
5. **Flow fingerprint.** Распределение размеров, направлений, пауз, bursts, длительность и периодичность keepalive видны даже при идеальном шифровании.
6. **Active probing.** Наблюдатель сам подключается к endpoint с корректными и некорректными сообщениями и классифицирует ответы.

Главный принцип camouflage: недостаточно правдоподобного первого пакета. Если ClientHello выглядит как Chrome с ALPN `h2`, а последующий поток не соблюдает HTTP/2 framing и типичные реакции сервера, маска распадается. Нужно приближать совместное распределение признаков всего flow, включая поведение на ошибки и неизвестных клиентов.

Active-probe resistance обычно требует, чтобы endpoint не отвечал узнаваемым протокольным сообщением до аутентификации. Непрошедшее проверку соединение должно выглядеть как обычный сервис, быть безопасно перенаправлено к нему либо завершаться так, чтобы реакция сама не стала уникальной сигнатурой.

## Модель безопасности VPN

VPN не даёт одну абстрактную «безопасность»; свойства зависят от противника и границы шифрования.

| Наблюдатель | Что VPN скрывает | Что остаётся видно или доверено |
|---|---|---|
| Атакующий в локальном Wi-Fi | внутренние адреса, DNS и payload при корректном full tunnel | факт соединения с VPN, размеры и timing |
| Провайдер | внутренние destinations и содержимое туннеля | IP VPN-сервера, объём, время, fingerprint внешнего протокола |
| Цензор | то же, что от провайдера | может блокировать endpoint, классифицировать flow и probing |
| VPN-провайдер/сервер | защищает участок клиент → VPN server от внешних наблюдателей | видит egress destinations и незашифрованный прикладной трафик |
| Сайт | скрыт исходный публичный IP клиента | видит IP VPN-сервера, аккаунт, cookies и browser fingerprint |
| Active MITM | не может незаметно изменить аутентифицированный tunnel | может блокировать, задерживать и пытаться подменить endpoint |

**Authentication** отвечает на вопрос, с тем ли peer установлено соединение. WireGuard проверяет владение static private key; OpenVPN обычно проверяет сертификат и proof of private key в TLS control channel. Один известный IP сервера не является аутентификацией.

**Key exchange** создаёт временные session keys по открытому каналу и является частью handshake самого VPN-протокола. Пользовательский TLS внутри туннеля — независимый обмен между приложением и сайтом. OpenVPN использует TLS для своего control plane; WireGuard использует Noise handshake.

**Forward secrecy** означает, что последующая кража долгосрочного ключа не должна раскрыть записанные прошлые сессии, если их ephemeral secrets уже уничтожены. Она не спасает от захваченного endpoint во время активной сессии.

**Replay protection** не позволяет принять старый зашифрованный пакет повторно. AEAD связывает ciphertext с nonce/counter и authentication tag, а получатель хранит окно уже принятых counters и отбрасывает дубликаты или слишком старые значения. Это действительно похоже на sequence number, но работает вместе с криптографической аутентификацией, а не как простой открытый счётчик.

**Rekeying** ограничивает объём данных под одним ключом и обновляет session state до исчерпания nonce space или по таймеру. **Endpoint compromise** остаётся фундаментальной границей: после расшифрования на VPN-сервере пакет идёт в Интернет. HTTPS внутри VPN сохраняет end-to-end шифрование до сайта; обычный HTTP — нет.

## Утечки: как трафик обходит ожидаемую политику

| Тип | Механизм | Защита |
|---|---|---|
| IP leak | маршрут или socket binding выбирает физический интерфейс | full-tunnel routes плюс firewall default-deny |
| DNS leak | resolver отправляет запрос вне туннеля | per-link DNS policy, блокировка неразрешённых resolvers, контроль DoH/DoT |
| IPv6 leak | VPN перехватывает только IPv4 | полноценные `::/0` routes и IPv6 firewall либо осознанное отключение IPv6 |
| WebRTC leak | ICE/STUN собирает кандидаты через путь, не охваченный политикой | охват UDP и обоих IP families, browser policy; relay-only при строгих требованиях |
| KillSwitch race | маршрут появляется до firewall-запрета или запрет снимается рано | атомарный порядок изменений и fail-closed reconnect |
| Split-tunnel bug | неверный prefix, mark или кеш домена выбирает прямой путь | проверка `route get`, тесты отрицательных сценариев, наблюдение интерфейсов |

WebRTC — браузерный набор API для peer-to-peer аудио, видео и данных. ICE собирает возможные адреса-кандидаты: локальные, публичные адреса NAT, обнаруженные через STUN, и relay-адреса TURN. Если STUN-пакеты уходят напрямую, удалённая сторона может увидеть публичный адрес обычного подключения; если весь IPv4/IPv6 и UDP корректно перехвачен, STUN увидит VPN egress. Современные браузеры ограничивают раскрытие локальных адресов, но полагаться только на это вместо сетевой политики нельзя.

## Инструменты Linux: какой слой проверяет каждая команда

Запоминать десятки флагов не нужно. Важно понимать вопрос, на который отвечает команда.

| Команда | Что проверяет |
|---|---|
| `ip link` | существуют ли интерфейсы, подняты ли они, какой MTU |
| `ip addr` | какие IPv4/IPv6-адреса и префиксы назначены интерфейсам |
| `ip route` | какие destination prefixes ведут к каким gateway/interface |
| `ip route get 8.8.8.8` | какой маршрут ядро выберет для конкретного пакета |
| `ip rule` | какие policy rules выбирают routing tables |
| `ss -tulpn` | какие TCP/UDP-сокеты слушают и каким процессам принадлежат |
| `ping` | отвечает ли endpoint по ICMP и какова задержка, но не «работает ли весь Интернет» |
| `tracepath` | последовательность hops и оценка PMTU без raw-socket требований `traceroute` |
| `traceroute` | где меняется/прерывается путь; режимы UDP, ICMP и TCP дают разные результаты |
| `dig` | прямой DNS-запрос и содержимое ответа |
| `resolvectl` | системные DNS-серверы, domains и per-link routing у `systemd-resolved` |
| `tcpdump` | реальные пакеты на выбранном интерфейсе до/после туннелирования |
| `nft list ruleset` | активная nftables policy, filter и NAT rules |
| `conntrack -L` | известные ядру состояния потоков и NAT mappings |

Одновременный capture особенно нагляден:

```bash
tcpdump -ni tun0
tcpdump -ni eth0 host 203.0.113.10
```

На `tun0` видны внутренние IP-пакеты с конечными destinations. На `eth0` — внешние зашифрованные пакеты к VPN endpoint. Если внутренний пакет есть, а внешнего нет, проблема между TUN и внешним сокетом/маршрутом. Если внешний запрос уходит, но ответа нет, проверяются сеть, сервер и firewall. Если ответ приходит на `eth0`, но не появляется расшифрованным на `tun0`, проблема в VPN state, ключах или обработке пакета.

## Диагностика по симптомам

### VPN подключён, но Интернет не работает

Проверка идёт от локального состояния к удалённому:

```{mermaid}
flowchart TD
    A[Есть адрес и UP state<br/>на tunnel interface?] -->|нет| B[Создание TUN и конфигурация адреса]
    A -->|да| C[route get выбирает туннель?]
    C -->|нет| D[Routes и policy rules]
    C -->|да| E[Внутренний пакет виден на TUN?]
    E -->|нет| F[Локальный firewall / socket policy]
    E -->|да| G[Внешний пакет уходит к endpoint?]
    G -->|нет| H[VPN process, endpoint route, KillSwitch]
    G -->|да| I[Сервер получает и decrypt?]
    I -->|нет| J[Ключи, transport, server firewall]
    I -->|да| K[FORWARD и NAT работают?]
    K -->|нет| L[ip_forward, firewall, conntrack, SNAT]
    K -->|да| M[Ответ возвращается?]
    M -->|нет| N[Удалённый маршрут / upstream / MTU]
    M -->|да| O[DNS и приложение]
```

### Работает адрес, не работает имя

Если запрос к `1.1.1.1` проходит, а `example.com` не резолвится, проверяются `resolvectl`, `dig`, выбранный DNS-сервер, маршрут к нему и firewall. Успешный `curl https://1.1.1.1` не всегда корректный тест HTTPS из-за сертификата и virtual hosting, но IP connectivity он помогает отделить от DNS.

### Маленькие ответы проходят, крупные TLS-соединения зависают

Первые кандидаты — MTU/PMTUD. TCP handshake и маленький HTTP-запрос помещаются, а крупный TLS record или сертификат упирается в black hole. Следует искать ICMP `Packet Too Big`, сравнивать MTU `tun0` и физического интерфейса, пробовать меньший размер и проверять MSS clamping.

### Туннель перестаёт принимать входящие после простоя

Если новый исходящий пакет мгновенно оживляет связь, вероятно, истёк NAT/UDP mapping. Keepalive должен быть достаточно частым для конкретного NAT, но не обязательно постоянным для peer, которому не нужны инициируемые снаружи пакеты.

### После включения full tunnel пропадает VPN-сервер

`ip route get VPN_SERVER_IP` покажет, не попал ли внешний endpoint в сам туннель. Исправление — host route, protected socket или policy rule, сохраняющая физический путь.

### KillSwitch блокирует LAN

Нужно отдельно проверить маршруты локальных префиксов и firewall chains. Одной записи `192.168.0.0/16 via wlan0` недостаточно, если OUTPUT policy запрещает физический интерфейс. Исключение должно одновременно разрешать маршрут и трафик, причём только для выбранной доверенной сети.

## Как одна модель реализуется на разных ОС

Задачи везде одинаковы: создать виртуальный интерфейс, назначить адреса и routes, указать DNS, исключить внешний socket из туннеля и применить блокирующую policy. API различаются.

### Linux

- TUN/TAP или kernel WireGuard создаёт виртуальный netdevice;
- netlink и iproute2 управляют addresses, routes и rules;
- nftables/netfilter фильтрует, маркирует и выполняет NAT;
- `systemd-resolved`/NetworkManager задаёт per-link DNS;
- systemd, D-Bus и capabilities помогают разделить privileged helper и UI.

### macOS и iOS

- `NEPacketTunnelProvider` запускает packet-tunnel extension;
- `NEPacketTunnelFlow` читает исходящие IP-пакеты и возвращает расшифрованные;
- `NEPacketTunnelNetworkSettings` задаёт addresses, included/excluded routes и DNS;
- система управляет жизненным циклом, разрешениями и маршрутизацией extension;
- доступность per-app и always-on режимов зависит от entitlement и managed policy.

### Windows

- виртуальный adapter представляет tunnel interface сетевому стеку;
- IP Helper/сетевые API читают и меняют routes и interface parameters;
- WFP фильтрует трафик на разных слоях, поддерживает stateful и per-application policy;
- Windows DNS Client и platform VPN configuration задают resolver policy;
- сервис с повышенными правами обычно отделён от пользовательского UI.

### Android

- приложение наследуется от `VpnService` и получает пользовательское разрешение;
- `VpnService.Builder` задаёт TUN address, routes, DNS и allow/deny applications;
- `establish()` возвращает file descriptor для чтения/записи IP-пакетов;
- `protect()` исключает внешний tunnel socket и предотвращает routing loop;
- always-on VPN и «block connections without VPN» дают системный вариант KillSwitch.

Платформенный API меняет форму интеграции, но не путь пакета: routing направляет внутренний IP в virtual interface, VPN-код оборачивает его во внешний transport, а обратный пакет проходит те же границы в обратном порядке.

## Сквозная проверка модели

Для закрепления полезно пройти один пакет и дать короткий ответ на каждом шаге.

1. Приложение вызывает `send()` на TCP/UDP socket; ядро формирует внутренний IP-пакет.
2. Policy rules выбирают routing table, longest prefix match — route и `tun0` либо физический интерфейс.
3. При VPN TUN передаёт внутренний пакет реализации протокола; userspace API или kernel module зависит от платформы.
4. VPN выполняет собственный handshake/key management, шифрует внутренний пакет и создаёт внешний UDP/TCP-пакет к endpoint.
5. Исключение `/32` или protected socket выводит внешний пакет через физическую сеть и не даёт ему вернуться в TUN.
6. VPN-сервер снимает внешний слой, firewall разрешает `FORWARD`, routing выбирает egress, SNAT делает source публично достижимым.
7. Conntrack выполняет reverse NAT ответа; сервер шифрует внутренний ответ и отправляет его клиенту.
8. Клиент расшифровывает пакет и инжектирует его через TUN; ядро доставляет данные исходному socket.
9. Если внешний UDP-пакет с внутренним TCP потерян, повтор выполняет внутренний TCP. Если потерян внутренний UDP, семантика приложения решает, нужен ли повтор.
10. MTU туннеля должен оставить место внешним заголовкам; PMTUD/PLPMTUD и MSS помогают не создавать black hole.
11. KillSwitch удерживает fail-closed policy во время всех переходов, а DNS и IPv6 входят в ту же модель трафика.
12. DPI видит outer endpoint и статистику flow; маскировка должна быть правдоподобна не только в первом пакете, но на протяжении всей сессии.

Эту цепочку можно проверить на небольшом стенде из Linux-клиента, Linux VPN-сервера и внешнего узла. `ip route get`, captures на `tun0` и `eth0`, `conntrack`, `nft` и `dig` превращают абстрактные термины в наблюдаемые переходы.
